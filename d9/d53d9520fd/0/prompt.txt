# 需求背景

主 agent 通过 subagent 扩展调用子 agent 时，子 agent 内部的工具调用（典型：bash 跑到死锁代码）可能永久卡住，导致整条链冻结。与用户讨论后定稿的方案是「两层超时 + 挂起裁决协议」：

## 第一层：bash-guard 扩展（新建）
- 订阅 pi 的 `tool_call` 事件，拦截 bash 工具调用
- 若子 agent 没传 `timeout` 参数 → 原地注入默认 300（秒）
- 显式传了 timeout → 原样尊重，不封顶、不修改
- pi 官方支持：`tool_call` handler 中 `event.input` 可变，原地修改会真实生效于执行（官方文档确认）。bash 工具输入 schema 是 `{ command: string; timeout?: number }`，不传 timeout 时 pi **没有**原生默认超时（源码确认 schema 描述为 "optional, no default timeout"）

## 第二层：subagent 扩展空闲看门狗 + 挂起裁决
- 监控子 pi 进程 stdout 的 NDJSON 事件流，固定 600s 无任何事件 → 判定空闲
- 空闲触发：对子进程**进程组**发 SIGSTOP（内核级冻结，全组：子 pi、它的 bash、死锁孙进程）
- 工具调用**提前返回**给主 agent 纯事实快照（不要任何建议性 hint，用户明确不要）：
  ```
  { status: "idle_suspended", suspensionId, idleMs,
    runningCommand,   // 当前 in-flight 命令原文（若有）
    requestedTimeout, // 该命令申请的 timeout（若有）
    tail }            // 最近若干条事件摘要（~10 条）
  ```
- 裁决协议：subagent 工具新增互斥参数 `resume` / `kill` / `inspect`（与现有 agent/tasks/chain 模式互斥）：
  - `resume: id` → SIGCONT 进程组，重挂 600s 看门狗，继续收集事件直到进程退出，返回最终结果
  - `kill: id` → 先 SIGCONT 再对进程组 SIGKILL（SIGSTOP 状态下 SIGTERM 投递不到），返回已收集的 transcript 收尾结果
  - `inspect: id, lines: N` → 返回更多日志行，不动进程
- 数字关系：600 > 300，默认路径命令超时报错事件必先于看门狗触发，不会误挂起；只有显式申请 >600s 静默窗口的才进入裁决

## 配套四件套（用户已确认）
1. **进程组管理**：spawn 改 `detached: true`，挂起/杀都作用于 `kill(-pid)` 整个进程组
2. **AbortSignal 生命周期修正**：现有 SIGTERM→5s→SIGKILL 监听器在工具提前返回后必须摘除，resume 时重挂；现有代码这条路径会误杀已挂起进程
3. **父进程退出清扫**：`process.on("exit")` best effort 对所有挂起中的进程组 SIGCONT+SIGKILL，防冻结进程泄漏
4. **parallel 挂起隔离**：一个任务挂起不中断兄弟任务；其余跑完后，parallel 调用返回「完成结果 + 挂起通知列表」，挂起的单独待处置

## 明确不做（用户拍板）
- 不做挂起 TTL、不做防乒乓球机制、不做任何建议性提示语（返回纯事实）
- 不做总时长 wall-clock 超时
- 不做环境变量加固（CI=1 等）
- Windows 兼容后置：SIGSTOP/SIGCONT 是 POSIX only，win32 下可优雅降级（如看门狗直接 kill 或 no-op，计划里定一个并说明理由）
